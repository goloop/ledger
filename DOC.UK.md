## Модель

Акаунт має **гаманець** із двома кошиками:

| Кошик | Чим поповнюється | Згоряє | Порядок витрат | Забирається поверненням коштів |
|---|---|---|---|---|
| `Bonus` | `Grant` | так, один строк на весь кошик | першим | ніколи |
| `Purchased` | `Deposit` | ніколи | другим | так |

Кожна зміна - це **запис** у журналі, який лише дописується: що змінилося,
баланси після зміни, ключ, що робить її ідемпотентною, і посилання. Записи
одного акаунта нумеруються 1, 2, 3, ... без пропусків. Гаманець - це сума
його історії, і `Audit` перевіряє, що це так.

**Резерв** - сума, відкладена для дії, яка ще не завершилася. Він пам'ятає, з
яких кошиків узяв кредити, тож повернення відновлює рівно те, що було взято.

Ledger ніколи не рахує ціну, не конвертує гроші й не спілкується з платіжним
провайдером. Це та частина білінгу, яка має бути правильною раніше за все
інше: баланс, за який клієнт заплатив.

## Створення ledger

```go
l := ledger.New(store)

l = ledger.New(store,
	ledger.WithClock(clock.Now),           // тести
	ledger.WithReleaseGrace(24*time.Hour), // див. «Резерви»
)
```

`Ledger` безпечний для конкурентного використання. Сховище впорядковує
оновлення одного акаунта; оновлення різних акаунтів ідуть паралельно.

## Суми

Суми - `int64` в одиниці, яку обирає застосунок. Зберігайте соті частки
кредиту, а не цілі кредити: тоді знижка 15% на ціну в один кредит має куди
подітися, а не округлюється до нуля.

Жодна сума і жоден кошик не можуть перевищити `MaxAmount` (2^53 - 1,
найбільше ціле, яке кожен JSON-читач зберігає точно). Це далеко за межами
будь-якого реального балансу: досягти його можна лише сумою з неперевіреного
вводу, і ledger відхиляє її з `ErrInvalid`, а не переповнюється.

Курс між грошима й кредитами належить застосунку, і після продажу кредитів
його варто зафіксувати: зміна курсу знецінює те, що клієнти вже мають.

## Ключі

Кожен метод, що змінює гаманець, приймає ключ, унікальний у межах акаунта.

- Повторний виклик з тим самим ключем нічого не змінює й повідомляє, що
  зробив перший: `Reverse` повертає ту саму суму, нарахування чи депозит
  нічого не роблять. `Hold` суворіший: без помилки лишається тільки виклик,
  що створив резерв, кожен повтор отримує резерв з `ErrHoldExists` (див.
  [Резерви](#резерви)).
- Виклик, що використовує ключ для іншого руху - іншого виду, іншої суми,
  іншого посилання, іншого походження бонусу, іншого `Exact` сторнування -
  завершується `ErrKeyReused`. Повтор має повторювати запит точно; новий
  запит потребує нового ключа. `Until` і `Replace` нарахування не
  порівнюються: їх вирішив перший виклик.
- Ключ - не довше `MaxKeyLength` (255) байт. Префікс `ledger:` зарезервовано
  для записів, які ledger робить сам (списання, повернення, згоряння).
- Ключі унікальні **в межах одного акаунта**. Платіж провайдера, зарахований
  двом акаунтам через хибний пошук, для ledger - два депозити; захист тут -
  рядок покупки в застосунку, що прив'язує платіж до одного акаунта.
  Називайте в ключі провайдера й середовище (`paddle:live:txn_01...`), щоб id
  двох провайдерів чи sandbox і продакшну ніколи не перетнулися.

Беріть ключі з того, за що платять:

| Рух | Ключ |
|---|---|
| Депозит за платіж | id транзакції провайдера |
| Сторнування за повернення | id вашого запису повернення - один на повернення, спільний для всіх шляхів, що його застосовують (див. [Відмова, повернення, chargeback](#відмова-повернення-chargeback)) |
| Оплата дії | id задачі, запиту чи замовлення |
| Щомісячний ліміт | період: `allowance:2026-09` |
| Вітальні кредити | `welcome` |

## Бонуси та їх згоряння

```go
err := l.Grant(ctx, account, ledger.Grant{
	Key:    "welcome",
	Amount: 300_00,
	Until:  time.Now().AddDate(0, 1, 0),
	Origin: ledger.OriginPromo, // за замовчуванням
	Note:   "welcome credits",
})
```

Бонусний кошик має **один строк**. Нарахування переносить його на `Until`,
якщо це пізніше, і ніколи - раніше, тож коротка акція не обрізає довше
нарахування.

Ліміт плану на новий період має замінювати попередній, а не додаватися до
нього. `Replace` списує залишок кошика (запис `expire`) і ставить строк
`Until`:

```go
err := l.Grant(ctx, team, ledger.Grant{
	Key:     "allowance:" + period.Format("2006-01"),
	Amount:  plan.MonthlyCredits,
	Until:   period.AddDate(0, 1, 0),
	Replace: true,
	Origin:  ledger.OriginPlan,
})
```

Резерв, що взяв бонусні кредити старого періоду і звільняється після
`Replace`, не переносить їх у новий період. Гаманець рахує свої періоди
(`Wallet.BonusPeriod`), кожен резерв пам'ятає, з якого періоду його бонусні
кредити, і звільнення в пізнішому періоді списує цю частину записом `expire`
одразу після `release` - так, як `Replace` зробив би, якби кредити лежали в
гаманці. Куплена частина повертається як звичайно.

`Origin` відділяє подарунок (`OriginPromo`: вітальні, бонус рівня, жест
доброї волі) від того, за що заплатив підписник (`OriginPlan`). Обидва
згоряють і витрачаються однаково; різниця - у тому, що бізнес винен, і
походження дозволяє відповісти на це згодом.

Згоряння **ліниве**. `Balance` показує прострочений кошик порожнім, нічого
не записуючи; наступний рух акаунта спершу записує `expire`. Сторінка
балансу, яку читають тисячу разів на день, не бере блокування.

## Депозити

```go
err := l.Deposit(ctx, account, ledger.Deposit{
	Key:    tx.ID,
	Amount: pack.Credits,
	Ref:    tx.ID,
})
```

Куплені кредити не згоряють. Викликайте `Deposit` з вебхука, що повідомляє
про оплату; повторна доставка нічого не змінює.

## Резерви

```go
h, err := l.Hold(ctx, account, ledger.Charge{Key: job.ID, Amount: price, Ref: "pdf-to-word"})
if err != nil {
	// *InsufficientError: гаманець не покриває суму.
	// ErrHoldExists: у задачі вже є резерв - її виконує інший воркер або вже
	// виконав. Не запускати; відповісти збереженим результатом задачі.
	return err
}

res, err := run(job)

settle, cancel := context.WithTimeout(context.WithoutCancel(ctx), 10*time.Second)
defer cancel()
if err != nil {
	_ = l.Release(settle, account, h.ID) // невдача нічого не коштує
	return err
}
if err := l.Capture(settle, account, h.ID); err != nil {
	// Дія виконана: тепер не звільняти. Списання доробить воркер.
	return settlements.Retry(ctx, account, h.ID)
}
return jobs.Done(ctx, job.ID, res)
```

- `Hold` забирає ціну з кошиків, спершу бонусні, і повертає резерв із
  `FromBonus` та `FromPurchased`.
- `Capture` робить його остаточним. Повторний `Capture` нічого не робить.
- `Release` кладе кредити назад у ті кошики, звідки їх узяли. Повторний
  `Release` нічого не робить, і `Release` списаного резерву теж нічого не
  робить.
- `Capture` повернутого резерву завершується `ErrReleased`: кредити вже
  повернулися, і дія виконалася неоплаченою. Що робити - списати ще раз чи
  пробачити - вирішує той, хто викликає.

**Без помилки лишається тільки виклик, що створив резерв.** Повтор з тим
самим ключем - повторений запит, другий воркер на тій самій задачі, двоє
одночасно - отримує існуючий резерв з `ErrHoldExists`, а також `ErrCaptured`
чи `ErrReleased`, якщо резерв уже завершено. Сховище впорядковує виклики,
тож резерв створює рівно один із них, і `if err != nil { return }` запускає
дію один раз. Знати резерв - не те саме, що знати результат дії: тримайте
його в записі задачі й відповідайте на повтор з нього. Нова спроба після
звільнення потребує нового ключа (`job-7:2`).

Сама дія має бути ідемпотентною назовні (власний id запиту до зовнішнього
API) або перевірною після: ledger робить так, що оплата відбувається один
раз, а не побічні ефекти.

Три правила тримають резерв чесним:

- **Release - лише в гілці невдачі, ніколи в `defer`.** Якщо дія виконалась,
  а `Capture` упав (база розірвала з'єднання), відкладений `Release` поверне
  кредити, і дія стане безкоштовною. Замість цього повторюйте `Capture` (він
  ідемпотентний) з воркера.
- **Розрахунок - на контексті, який клієнт не скасує, з власним строком.**
  Запит, чий клієнт відключився, скасовує свій контекст; і `Capture`, і
  `Release` впадуть, а резерв чекатиме `ReleaseStale` - який подарує
  виконану дію. `context.WithoutCancel(ctx)` зберігає значення запиту і
  прибирає і скасування, і строк, тож дайте йому власний таймаут.
- **Тримайте воркер розрахунків.** `Capture`, що падає після виконаної дії, -
  це задача на повтор до успіху, а не причина звільняти.

Коли бонусні кредити повертаються, а кошик за час дії вже згорів, вони
отримують пільговий строк (`DefaultReleaseGrace`, 24 години), а не
приходять уже згорілими. Бонусні кредити, що повертаються до строку,
зберігають його. Бонусні кредити періоду, який завершив `Replace`,
списуються (див. [Бонуси та їх згоряння](#бонуси-та-їх-згоряння)).

## Spend

```go
err := l.Spend(ctx, account, ledger.Charge{Key: req.ID, Amount: price, Ref: "tts"})
```

Резерв і списання одним записом - для дії, яка не може зірватися після
оплати.

## Сторнування

```go
taken, err := l.Reverse(ctx, account, ledger.Reversal{
	Key:    adjustment.ID,
	Amount: purchase.Credits,
	Ref:    adjustment.TransactionID,
	Note:   "chargeback",
})
if taken < purchase.Credits {
	// клієнт уже витратив частину: зафіксуйте втрату
}
```

Сторнування забирає куплені кредити після того, як гроші повернулися, не
більше суми:

1. те, що лишилося в кошику куплених;
2. потім куплену частину резервів, що ще в дорозі. Кожен резерв записує
   забране в `Hold.Reversed`, і звільнення повертає лише решту. Без цього
   клієнт міг би запустити дію, повернути гроші, дати дії впасти й лишити
   собі кредити.

Уже витрачене лишається витраченим: дія, за яку заплатили, виконалась.
Бонусні кредити не забираються ніколи. Запис фіксує запит і результат
числами: `Requested`, `FromHolds`, а також `Taken()` і `Short()`, обчислені з
них. Повторний виклик з тим самим ключем повертає той самий `taken`; виклик
з іншою сумою завершується `ErrKeyReused`.

`Exact` бере всю суму з кошика куплених або нічого, з `*InsufficientError`.
Кредити в резервах не враховуються: дія в дорозі - це використання. Це
атомарна перевірка, що **вільних куплених кредитів** вистачає, - а не доказ,
що конкретний пакет не використано. Куплені кредити - один кошик: купити
пакет, витратити все, купити другий, і `Exact`-сторнування першого пройде
коштом другого. Якщо право на повернення залежить від того, що пакет не
використано, застосунок вирішує це за власними записами (що й коли куплено,
що витрачено відтоді), а `Exact` охороняє сам момент списання.

## Коригування

```go
err := l.Adjust(ctx, account, ledger.Adjustment{
	Key:       "ticket-4711",
	Purchased: 50_00,
	Note:      "support: failed conversion charged twice",
})
```

Ручне виправлення оператором: додатні суми додають, від'ємні забирають, і
жоден кошик не опускається нижче нуля. Додавання бонусних кредитів у кошик
без строку потребує `BonusUntil`.

## Баланс та історія

```go
w, err := l.Balance(ctx, account)           // Bonus, Purchased, BonusExpiresAt, Seq
page, err := l.Entries(ctx, account, 0, 50) // найновіші першими
next, err := l.Entries(ctx, account, page[len(page)-1].Seq, 50)
```

Акаунт без жодного запису читається як порожній гаманець, а не як помилка.

## Аудит

```go
if err := l.Audit(ctx, account); errors.Is(err, ledger.ErrCorrupt) {
	// історія не сходиться: тривога, а не автовиправлення
}
```

`Audit` перечитує всю історію: нумерація без пропусків, кожен записаний
баланс дорівнює попередньому плюс рух, жоден кошик не нижче нуля, перший
запис починається з порожнього гаманця, останній баланс дорівнює гаманцю.

Він не бере блокування і безпечний на живій системі: спершу читає гаманець і
перевіряє записи до його `Seq`, які вже не змінюються, тож рух під час
аудиту не виглядає як пошкодження. Історію він проходить посторінково, від
найновіших, не тримаючи її в пам'яті. Але читає всі записи, тож запускайте
його з задачі звірки, а не з запиту.

## Завислі резерви

```go
n, err := l.ReleaseStale(ctx, 30*time.Minute, 100)
```

Повертає резерви, що тримаються довше заданого віку - їх лишив процес, який
упав між резервом і його завершенням, - і каже, скільки повернув, не більше
ліміту (обмеженого 1000).

Резерв, який не вдалося повернути, не зупиняє прохід і не заступає резерви
за ним: прохід іде завислими резервами посторінково, в порядку створення,
повз кожну невдачу, доки не поверне ліміт або не перегляне всі. Помилки
повертаються разом, поруч із лічильником. Зупиняє лише скасований контекст.

Запускайте з періодичного воркера, з віком, помітно більшим за найповільнішу
дію **і** за час, протягом якого повторюється невдалий `Capture`. Прохід
знає лише вік резерву, а не те, чи його дія виконалась чи ще триває: резерв,
чия дія відомо що виконана, належить воркеру розрахунків, і звільнення його
за віком дарує дію.

## Моделі ціноутворення

Ledger переміщує кредити; ціни, пакети, плани та їхні права належать
застосунку. Цей розділ показує, як кожна поширена модель лягає на ledger і
де він - не той інструмент.

Решту роботи в кожній моделі нижче роблять дві таблиці:

- **purchases** - рядок на кожен checkout: акаунт, що куплено, сума,
  кредити, id транзакції провайдера, статус;
- **entitlements** - що акаунт може робити зараз: план, його ліміти, до
  коли. Джерело правди про гроші - провайдер, про права - ця таблиця.

### Кредити, оплата за дію

Клієнт купує пакет; кожна дія має ціну в кредитах, яку видно до запуску.
Хто користується багато - платить більше, хто мало - мало, місяць без
використання нічого не коштує.

```go
// Checkout: сума береться з вашої таблиці пакетів, ніколи не від клієнта.
// Вебхук, транзакцію завершено:
err := l.Deposit(ctx, p.Account, ledger.Deposit{Key: tx.ID, Amount: p.Credits, Ref: tx.ID})

// Кожна дія:
price := priceBook[feature] // 0 - безкоштовно: ledger не чіпаємо
h, err := l.Hold(ctx, account, ledger.Charge{Key: job.ID, Amount: price, Ref: feature})
// ... виконати, потім Capture чи Release
```

Знижка за обсяг - це більше кредитів за ті самі гроші (`Credits` більшого
пакета), а не дешевший кредит: вартість одного кредиту лишається сталою, тож
ціна в кредитах завжди має одну відповідь у грошах.

### Окремі платні речі

Клієнт бачить річ із ціною - «Галерея, 25 GB на 15 днів: €1.50» - і платить
її з гаманця. Кредити лишаються у фоні; гаманець - це спосіб не платити
комісію картки за кожну дрібну ціну.

```go
err := l.Spend(ctx, account, ledger.Charge{
	Key:    "gallery:" + g.ID + ":create",
	Amount: item.Price,
	Ref:    "gallery-25gb-15d",
})
if err == nil {
	err = galleries.Activate(ctx, g.ID, time.Now().AddDate(0, 0, 15))
}
```

Продовження - ще одна річ зі своїм ключем (`gallery:<id>:extend:2`).

### План з лімітом

Підписка дає кредити на кожен період; вони згоряють разом із періодом і не
накопичуються. Сама підписка живе в платіжного провайдера; ledger тримає
ліміт.

```go
func grantAllowance(ctx context.Context, sub Subscription, month time.Time) error {
	start := time.Date(month.Year(), month.Month(), 1, 0, 0, 0, 0, time.UTC)
	return l.Grant(ctx, sub.Account, ledger.Grant{
		Key:     "allowance:" + sub.ID + ":" + start.Format("2006-01"),
		Amount:  sub.Plan.MonthlyCredits,
		Until:   start.AddDate(0, 1, 0),
		Replace: true,
		Origin:  ledger.OriginPlan,
	})
}
```

Викликайте, коли підписка стає активною (вебхук), і з щоденної задачі для
кожної підписки, чий оплачений період покриває сьогодні. Ключ робить щоденну
задачу безпечною хоч за якої частоти; `Replace` списує залишок минулого
місяця; `OriginPlan` фіксує, що за це заплачено, тож на ваш розсуд його не
забрати.

### План + понад ліміт

Нічого додаткового: ліміт - це бонусні кредити, вони витрачаються першими,
решту оплачують куплені з пакетів. Підписник, якому треба більше, купує
пакет; клієнт без плану користується лише пакетами.

### Строки: місяць, рік, два роки

Строк - це те, як клієнт платить: $15 на місяць, $60 на рік, $100 за два
роки. Він належить підписці провайдера (`billing_cycle` у Paddle, період
оплати продукту в Creem). Ліміт однаково варто нараховувати **щомісяця**,
хоч який строк: річний план, що нарахував би дванадцять місяців одразу,
дозволив би витратити річний ліміт за тиждень і скасувати. Рецепт вище вже
так і робить - нараховує помісячно, поки триває оплачений період.

Довгі передоплачені строки - це зобов'язання: план на два роки - це сервіс,
який ви винні два роки, і закриття продукту раніше означає повернення
невикористаної частини.

### Безкоштовний рівень і акції

```go
// Вітальні кредити після підтвердження email.
_ = l.Grant(ctx, account, ledger.Grant{Key: "welcome", Amount: 300_00, Until: now.AddDate(0, 1, 0)})

// Щомісячний бонус для тих, хто заплатив і не повернув покупку.
_ = l.Grant(ctx, account, ledger.Grant{
	Key: "bonus:" + now.Format("2006-01"), Amount: 100_00, Until: nextMonth,
})
```

Хто заслуговує на бонус - підтверджений email, покупка після строку відмови,
рівень витрат - це політика, і вона лишається в застосунку. Денна безкоштовна
квота на інструмент («3 конвертації на день») - це обмеження частоти, а не
кредити.

### Гаманець команди

Акаунт - це той, кому належить баланс: id користувача, команди, тенанта. Хто
може з нього витрачати - перевірка прав застосунку перед `Hold`.

### Відмова, повернення, chargeback

**Одне повернення - одне сторнування, хоч хто його почав.** Відмова
починається у вашому застосунку і підтверджується вебхуком провайдера;
повернення з дашборду провайдера чи chargeback починається з вебхука. Якби
ці шляхи мали різні ключі - тут `withdraw:<покупка>`, там id adjustment, -
одне повернення сторнувалося б двічі. Тому кожне повернення спершу отримує
запис у вашій базі, і його id - ключ на кожному шляху:

```go
// Відмова від пакета, у транзакції, що блокує покупку.
r, err := refunds.Open(ctx, p, refunds.Withdrawal) // ваша таблиця: рядок на повернення
rev := ledger.Reversal{Key: "refund:" + r.ID, Amount: p.Credits, Ref: p.TransactionID, Exact: true}
r.SaveReversal(rev) // зберігається з рядком, тож кожен шлях надсилає той самий запит
if _, err := l.Reverse(ctx, p.Account, rev); err != nil {
	return err // *InsufficientError: вільних куплених кредитів бракує
}
// Далі попросити провайдера; зберегти його id повернення в r. Після таймауту
// спершу знайти повернення в провайдера, а не просити ще раз.

// Вебхук повернення чи chargeback, у транзакції, що блокує покупку: знайти
// запис за id провайдера; інакше відкриту відмову цієї покупки ще без id
// провайдера (вебхук може прийти раніше, ніж збережено відповідь API);
// інакше відкрити новий.
r, err := refunds.ForProvider(ctx, p, adj.ID)
_, err = l.Reverse(ctx, p.Account, r.Reversal()) // нічого не робить, якщо вже застосовано
```

- Шлях вебхука повторює збережене сторнування точно - той самий ключ, сума й
  `Exact`, - тож нічого не змінює, якщо відмова вже його застосувала, і дає
  `ErrKeyReused`, якщо щось відрізняється.
- Повернення, остаточно відхилене провайдером, скасовується компенсаційним
  рухом із ключем запису:
  `Adjust{Key: "refund-undone:" + r.ID, Purchased: taken}`.
- Кілька часткових повернень однієї покупки - кілька записів; обмежуйте їхню
  суму тим, що покупка дала, у власних записах.
- Повернення, що прийшло раніше за вебхук самого платежу, не можна загубити,
  і за ним не має йти депозит за повернений платіж: тримайте стан покупки, і
  нехай його перевіряють і `Deposit`, і `Reverse`.
- `Exact` перевіряє, що вільних куплених кредитів вистачає, а не що цей
  пакет не використано (див. [Сторнування](#сторнування)).

### Де ledger - не той інструмент

- **Безлімітні плани** («$60 на рік, конвертації без ліміту, не більше N на
  годину»): рахувати нічого. Перевірте право, застосуйте обмеження частоти,
  а ledger не залучайте.
- **Оренда місткості** («50 GB на рік, скільки завгодно галерей»):
  місткість - це ліміт на те, що існує, а не баланс, що витрачається;
  видалений файл повертає місце. Тримайте ліміт у праві й порівнюйте з тим,
  що збережено.
- **Разові ліцензії** («Maker, $59, оновлення 12 місяців»): право з датою,
  продане провайдером, записане в таблицю прав.

Один продукт може їх поєднувати: план місткості з кредитами на AI-додатки,
безлімітний план із платним доповненням. Тоді ledger несе лише ту частину,
що витрачається.

## Як написати сховище

`MemoryStore` - для тестів і однопроцесних інструментів. Сервіс тримає
ledger у своїй базі, і це сховище - код застосунку; пакет не залежить від
жодного драйвера.

Контракт невеликий:

- **`Update` атомарний і послідовний для акаунта.** Заблокувати гаманець,
  викликати `fn`, записати його `Change` (гаманець замінено, записи дописано,
  резерви вставлено чи замінено за id) у тій самій транзакції. Два оновлення
  одного акаунта ніколи не перемежовуються.
- **Новий акаунт теж блокується.** Створіть рядок гаманця до блокування,
  інакше два перші оновлення проскочать одне повз одне.
- **Ключі унікальні в межах акаунта**, і база це гарантує: зміна з ключем,
  який акаунт уже має, відхиляється цілком з `ErrDuplicateKey`.
- **`fn` може виконатися кілька разів**, якщо база перервала транзакцію і
  сховище повторює; побічних ефектів він не має.
- **Помилка з `fn` чи nil `Change` нічого не записують.**
- **`View.Held` повертає відкриті резерви акаунта**, найстаріші першими, як
  їх востаннє записано. Він працює під тим самим блокуванням, тож список не
  зміниться, поки його використовує сторнування.
- **`StaleHolds` впорядковує за `(created_at, id)`** і продовжує після пари,
  заданої в `StaleQuery`, тож прохід іде повз резерви, що постійно падають.

У PostgreSQL блокування - це `SELECT ... FOR UPDATE` рядка гаманця після
`INSERT ... ON CONFLICT DO NOTHING`, що створює цей рядок:

```sql
CREATE TABLE ledger_wallets (
    account          text PRIMARY KEY,
    bonus            bigint NOT NULL DEFAULT 0 CHECK (bonus >= 0),
    purchased        bigint NOT NULL DEFAULT 0 CHECK (purchased >= 0),
    bonus_expires_at timestamptz,
    bonus_period     bigint NOT NULL DEFAULT 0,
    seq              bigint NOT NULL DEFAULT 0,
    updated_at       timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE ledger_entries (
    account         text   NOT NULL,
    seq             bigint NOT NULL,
    kind            text   NOT NULL,
    key             text   NOT NULL,
    bonus           bigint NOT NULL,
    purchased       bigint NOT NULL,
    bonus_after     bigint NOT NULL,
    purchased_after bigint NOT NULL,
    hold            text   NOT NULL DEFAULT '',
    requested       bigint NOT NULL DEFAULT 0,
    from_holds      bigint NOT NULL DEFAULT 0,
    exact           boolean NOT NULL DEFAULT false,
    origin          text   NOT NULL DEFAULT '',
    ref             text   NOT NULL DEFAULT '',
    note            text   NOT NULL DEFAULT '',
    at              timestamptz NOT NULL,
    PRIMARY KEY (account, seq),
    UNIQUE (account, key)
);

CREATE TABLE ledger_holds (
    id             text PRIMARY KEY,
    account        text   NOT NULL,
    key            text   NOT NULL,
    amount         bigint NOT NULL,
    from_bonus     bigint NOT NULL,
    from_purchased bigint NOT NULL,
    reversed       bigint NOT NULL DEFAULT 0,
    bonus_period   bigint NOT NULL DEFAULT 0,
    ref            text   NOT NULL DEFAULT '',
    status         text   NOT NULL CHECK (status IN ('held', 'captured', 'released')),
    created_at     timestamptz NOT NULL,
    settled_at     timestamptz,
    CHECK (amount = from_bonus + from_purchased),
    CHECK (reversed BETWEEN 0 AND from_purchased)
);
CREATE INDEX ledger_holds_stale ON ledger_holds (created_at, id) WHERE status = 'held';
CREATE INDEX ledger_holds_open ON ledger_holds (account, created_at) WHERE status = 'held';

-- The history is append-only: refuse any change to it.
CREATE FUNCTION ledger_entries_append_only() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
    RAISE EXCEPTION 'ledger_entries is append-only';
END $$;
CREATE TRIGGER ledger_entries_append_only BEFORE UPDATE OR DELETE ON ledger_entries
    FOR EACH ROW EXECUTE FUNCTION ledger_entries_append_only();
```

Первинний ключ `(account, seq)` - друга лінія оборони: сховище, що забуло
про блокування, голосно падає на ньому замість тихо загубити рух. Обмеження
`CHECK` і тригер змушують базу відхиляти те, чого ledger ніколи не пише:
резерв, частини якого не сходяться, невідомий статус і будь-яку зміну
історії. Ставте в транзакції `SET LOCAL lock_timeout`, щоб один завислий
запит не вишиковував за собою всі інші запити акаунта.

Потім доведіть це:

```go
func TestPostgresStore(t *testing.T) {
	ledgertest.Store(t, func(t *testing.T) ledger.Store {
		return newPostgresStore(t) // порожнє, прибирається через t
	})
}
```

`ledgertest.Store` перевіряє кожне правило вище, включно з конкурентними
оновленнями одного акаунта; сховище без блокування рядка його не проходить.

## Помилки

| Помилка | Значення |
|---|---|
| `ErrInvalid` | відхилено до звернення до гаманця: порожній чи зарезервований ключ, недодатна сума чи більша за `MaxAmount`, строк у минулому; також рух, що вивів би кошик за `MaxAmount` |
| `ErrInsufficient` / `*InsufficientError` | гаманець не покриває суму; `Required` і `Available` кажуть, наскільки |
| `ErrNotFound` | резерву немає в цьому акаунті |
| `ErrHoldExists` | `Hold`, повторений з ключем наявного резерву; резерв повертається разом з нею |
| `ErrCaptured` | разом з `ErrHoldExists`: цей резерв списано |
| `ErrReleased` | `Capture` резерву, який уже повернуто; разом з `ErrHoldExists` - `Hold`, повторений з його ключем |
| `ErrKeyReused` | ключ використано для іншого руху |
| `ErrDuplicateKey` | повертає `Store`; означає, що сховище перевіряло й писало в різних транзакціях |
| `ErrCorrupt` | `Audit` знайшов історію, що не сходиться |

Помилки сховища повертаються як є.

## Межі пакета

Свідомо не тут: ціни, курси, пакети кредитів, плани, правила вітальних і
щомісячних бонусів, право відмови від договору, платіжні провайдери й
вебхуки. Вони різні в кожному продукті й змінюються разом із бізнесом;
ledger під ними змінюватися не повинен.

Що таке ledger, і чим він не є:

- Журнал внутрішніх кредитів у двох кошиках, а не подвійний запис
  бухгалтерії: без валют, покупок, дебіторської заборгованості чи розрахунків
  із платіжним провайдером. Це живе у власних таблицях застосунку.
- `Audit` доводить арифметику історії й гаманця. Він не судить, чи рух був
  правильним: узгоджений, але хибний рух пройде.
- `MemoryStore` втрачає все при перезапуску. Справжнім грошам потрібне
  сховище в базі, перевірене `ledgertest.Store` і тими збоями, яких набір
  не імітує: commit, відповідь на який загубилася, перезапуск, deadlock.
- `MaxAmount` обмежує кожен кошик, а не їхню суму: `Total` може сягнути
  вдвічі більшого, що `int64` вміщує, а JSON-читач із числами float64 - ні.
